# Lot D — Automatisations locales (3.4.0-dev)

- 16 emplacements, tous inactifs par défaut. L'action 0 désactive la règle. Les règles sont évaluées une fois par seconde, indépendamment du Wi-Fi.
- Une plage est semi-ouverte [début, fin). Lorsqu'elle traverse minuit, ses filtres calendaires correspondent à la date du début de la plage. Les jours sont un masque dimanche=1, lundi=2, ..., samedi=64. Mois/jour 0 = tous. Les dates sont récurrentes chaque année.
- Thèmes usine (index stable 0–8 : Warm White, Ocean, Sunset, Forest, Aurora, Ocean Pulse, Aurora Flow, Rainbow, Ember), plafond de luminosité 0–100 % du maximum, ou animation ponctuelle (1–6, réglages de durée et d'intensité du lot C). Pour une animation, début=fin. Pour une plage, début et fin doivent différer.
- Le numéro de règle le plus élevé gagne par type d'action. Une règle de thème et une règle de luminosité peuvent coexister. Les règles de thème ne modifient pas le thème manuel ni les réglages de luminosité individuels, et ne sont pas réécrites dans les paramètres à chaque changement. L'interface principale représente toujours le réglage manuel, pas le rendu temporaire. Mode nuit, extinction manuelle, aperçu et maintenance priment. Le réglage global des animations doit être actif pour lancer un événement.
- Événements uniquement au franchissement naturel d'une minute. Pas de rattrapage au démarrage, après une longue suspension ou après un saut horaire. Déduplication par emplacement et date locale en RAM : une correction en arrière ou le double passage à l'heure d'hiver ne rejoue pas un événement déjà consommé durant ce démarrage. Un événement ignoré pendant le mode nuit n'est pas rejoué. Le compteur est perdu au redémarrage ; un événement futur peut être déclenché à nouveau après un redémarrage suivi d'un recul de l'heure. Modifier une règle déjà déclenchée peut également empêcher son nouveau déclenchement le même jour.
- GET /api/automations retourne {version:1,rules:<288 caractères hexadécimaux>}. POST même route, formulaire rules=<hex>, en-tête X-Wordclock-Action: automations, refus en maintenance. L'édition/export JSON lisible est côté navigateur : {version:1,rules:[16 objets start,end,days,month,day,action,value]}. Pas de code exécutable. Les importations ne sont appliquées qu'après enregistrement. Pas de thèmes personnels automatisés, météo ni lever/coucher du soleil dans ce lot.
- Stockage indépendant /config/rules.dat, .tmp, .bak. Format : 288 caractères hex puis 4 octets checksum FNV-1a little endian. Vérification avant activation, sauvegarde de l'ancien fichier valide. Les deux types de reset du firmware 3.4 effacent ou désactivent les règles. Un ancien firmware ignore ces fichiers ; son reset ne les connaît pas.
- Budget cible <512 octets supplémentaires de RAM statique (à vérifier avec PlatformIO). Assertion de compilation sur les trois principales structures <320 octets ; résolution d'un thème à l'entrée de plage avec document JSON temporaire 768 octets. Aucun nouveau buffer LED. Pas de test matériel dans l'environnement de préparation.
- Validation : outils existants + tests natifs `test/rules_native/test.cpp`, contrôle de l'API dans `tools/validate.py`. Tests manuels utiles : créer une plage temporaire, vérifier restauration du thème, créer un événement pour la prochaine minute et vérifier le mode nuit. Tester les resets et l'interruption de sauvegarde avant stable.
