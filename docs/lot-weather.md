# 3.5.0-dev — Weather (experimental)

Disabled initially. Enter decimal latitude/longitude in Settings > Météo. Configuration is stored in LittleFS; weather readings remain in RAM. A normal successful fetch is scheduled every 30 minutes; failures retry after five minutes, manual refresh is rate limited to ten seconds. Data expire after two hours. No weather fetch while firmware/web maintenance is active. A valid clock and Wi-Fi are required. Weather affects the selected zones, preserving brightness; preview, night and programmed themes take priority. A programmed brightness limit still applies. Forecast mode selects the first hourly record at least 30 minutes after the current record; the temperature shown is always current.

HTTP is unauthenticated and unencrypted. The provider receives coordinates; responses are restricted to validated weather data and cannot change settings. Only fixed host/endpoint, no redirects enabled. Open-Meteo attribution in UI; confirm commercial terms before distribution. The HTTPClient transport uses HTTP/1.0 and a bounded sink (1535 bytes max, HTTPClient handles chunk framing). It is synchronous: the 1800 ms read timeout is an inactivity timeout, not a hard end-to-end deadline. DNS/connect and multiple reads may take longer. This needs a device test; no assurance of real-time rendering during fetch yet. Memory guard is heuristic, not proof of peak allocation safety.

Test locally with mode disabled first, then enable rear only with known coordinates. Check current and forecast separately, monitor /api/weather and /api/system, exercise failed connection and recovery. Do not publish a stable release before device tests. Native tests cover palette mapping and expiry arithmetic, not HTTP or LittleFS integration. Preview is illustrative, not a pixel-accurate simulator. No city geocoding in this version.
